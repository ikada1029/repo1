## 2. 기능 규격

### 2.1 `guard.recipe` — 레시피 필터

- **방식:** 서버가 레시피를 로드·리로드할 때(후보: `RecipeManager` 적용 시점의 리로드 리스너/믹스인) 전체 레시피를 순회해 **허용 목록에 없는 레시피를 제거**한다. 데이터팩 오버라이드에만 의존하지 않는다(동적 생성 레시피, 호환 모드가 런타임에 만드는 레시피 대응).
- **범위:** 모든 네임스페이스·레시피 타입(작업대, 화로 계열, 대장간, 그리고 Farmer's Delight·Kaleidoscope Cookery의 조리 타입).
- **정책:**
  - 기본값은 `deny`. 허용은 `recipe_id`, `recipe_type`, `result_item`, `namespace` 단위의 화이트리스트로 명시한다.
  - 허용 레시피에는 `job`, `min_level`, `station` 같은 **요구 조건 메타데이터**를 붙일 수 있다.
- **리로드:** `/economycore reload`로 서버 재시작 없이 재적용. 적용 결과(제거/유지 수)를 로그로 남긴다.
- **완료 조건:** G1 X2 — 모든 모드에서 제한 대상 결과물 제작 불가.

### 2.2 `guard.craft` — 결과 슬롯 검증 (이중 방어)

- 레시피 필터를 통과한 뒤에도, **결과 아이템 수령 시점**에 서버가 허용 여부를 재검증한다.
- 대상 후보: 제작 결과 수령, 모루·숫돌·대장간 작업대·마법부여 이벤트, 화로 수령, 타 모드 작업대 메뉴.
- 거부 시 결과 슬롯을 비우고 `CRAFT_DENIED` 로그를 남긴다.

### 2.3 `guard.durability` — 무한 내구도

- 코어가 발급하는 장비에 **무적(unbreakable) 데이터 컴포넌트**를 부여한다.
- 컴포넌트를 무시하는 타 모드 도구를 위해 **내구도 감소 호출 차단**을 보조로 둔다(후보: 아이템 손상 처리 지점의 훅).
- 무한 내구도와 무한 탄약/물/재료를 **혼동하지 않는다**(명세 3.2장). 탄약·충전량은 이 모듈 범위 밖.

### 2.4 `guard.command` — 명령어와 게임모드

- 일반 플레이어의 `/give`, `/summon`, `/setblock` 등 아이템·블록 생성 명령은 권한 레벨로 차단한다.
- 크리에이티브 모드는 관리자만 허용하고, **관리자 발급은 모두 `admin_audit`에 기록**한다.
- 크리에이티브 인벤토리를 통한 유입은 관리자 외에는 불가능해야 한다.

### 2.5 `guard.identity` — 발급 장부와 시리얼

- 코어가 발급하는 아이템에 커스텀 데이터 컴포넌트 `economycore:identity`를 부여한다.

```text
identity = { serial: uuid, kind: "tool|gear|furniture|gun", owner: uuid|null,
             issued_event: event_id, issued_at: epoch_ms }
```

- 발급은 **장부(`persistence`)에 먼저 기록**한 뒤 아이템을 지급한다(명세 14.2장 멱등성).
- 같은 `serial`이 두 곳에서 관측되면(복제 의심) 로그를 남기고 운영 알림을 보낸다.
- 타 모드 NBT/컴포넌트와의 충돌은 네임스페이스 접두(`economycore:`)로 회피하고, G1에서 충돌 여부를 확인한다(X7).

### 2.5.1 `platform.lockcheck` — locklist 검증

- 서버 기동 시 로드된 모드의 **파일명·버전·해시**를 `locklist` 설정과 대조한다. 불일치 시 경고 또는 기동 거부(설정 가능).
- 클라이언트 접속 시 모드 목록 불일치 탐지는 가능한 범위에서 구현한다(명세 18장 버전 불일치 탐지).

### 2.6 `guard.melee` — 근접 공격 서버 재검증

> **적용 조건(D-006):** LR 근접 백엔드를 쓰는 경우에만 필요하다. 바닐라 백엔드(1차)에서는 대상 선정이 서버 측 바닐라 로직이라 이 모듈의 핵심 위협(T1·T2)이 사라진다. LR 이식 단계(FX5, GB-5)에서 활성화한다.

> 배경: LR 근접 무기는 **타격 대상 선정을 클라이언트가 하고 서버는 거리만 확인**한다(`melee-system-findings.md` 10.3). PvP·보스 기여도·랭킹을 쓰는 서버에서는 변조 클라이언트가 원뿔 각도·벽·시야를 무시하고 사거리 안의 임의 엔티티를 칠 수 있다. 이 모듈이 서버에서 다시 검증한다. 상태: **[제안]**, 구현 방식은 C0 스파이크에서 확정.

#### 2.6.1 위협 모델

| # | 위협 | 현재 LR 동작 | 대응 |
|---|---|---|---|
| T1 | 대상 임의 지정(각도·벽 무시) | 서버는 `거리² ≤ 사거리²`만 확인 | 서버가 대상 후보를 재계산해 **교집합만 인정** |
| T2 | `delay` 무시(준비 직후 즉시 전송) | 준비 상태·쿨다운만 확인 | 준비 시각 기록 후 **허용 시간창** 밖의 패킷 폐기 |
| T3 | 한 패킷에 과다 대상 | 패킷당 대상 수 상한 설정 있음 | 상한 유지 + 무기·히트박스별 이론적 최대 대상 수로 추가 제한 |
| T4 | 시선·위치 위조(`CPrepareMeleeAttack`이 origin/direction을 실어 보냄) | 서버의 사용 여부 `[확인 필요]` | 검증에는 **서버가 가진 플레이어 눈 위치·시선만 사용**, 클라이언트 값은 신뢰하지 않음 |
| T5 | 쿨다운·콤보 카운터 조작 | 서버가 쿨다운 틱과 `actionCount` 일치 확인(양호) | 유지, 위반 시 로그 |
| T6 | 엔티티 ID 추측으로 원거리 대상 지정 | 거리 확인만 | T1 재계산으로 해소 |

#### 2.6.2 검증 규칙

공격 요청(`postAttack`에 해당하는 시점)마다 서버가 다음을 수행한다.

```text
1. 준비 상태 확인: 서버 기록 prepare_tick 이 존재하고 현재 틱 - prepare_tick 이
   [delay - tick_tolerance, delay + delay_window_ticks] 범위 안인가 (T2)
2. 서버 재계산: server_targets = weapon.collectTargets(player, stack, action,
   player.eyePosition(서버값), player.lookAngle(서버값))        // 같은 필터(원뿔/OBB) 서버 실행
3. 지연 보상(선택): 레이턴시를 고려해 히트박스를 완화하거나 과거 위치 이력으로 재판정
   (range_tolerance, angle_tolerance_deg, latency_comp_ms)
4. 시야 검사(선택): 공격자 눈 → 대상 사이 블록 차폐 레이캐스트(require_los)
5. 최종 대상 = client_targets ∩ server_targets_with_tolerance
   (클라이언트가 보낸 ID 중 서버가 인정하는 것만 피해 적용)
6. 수 제한: min(max_targets_per_packet, 해당 히트박스의 최대 대상 수)
7. 불일치가 있으면 감사 로그 기록(8장 형식)과 위반 점수 누적
```

- `server_targets`가 비어 있으면 클라이언트 목록이 있어도 **피해 0**으로 처리한다(허공 공격은 정상 동작으로 허용).
- 정상 클라이언트의 경계 판정 오차(핑 100~200ms 환경)를 **허용 오차**로 흡수해 오탐을 최소화한다. 오차 기본값은 [제안]이며 실측으로 조정한다.

#### 2.6.3 동작 모드와 위반 처리

| 모드 | 동작 | 용도 |
|---|---|---|
| `off` | 검증 안 함 | 비교용 |
| `log_only` | 판정은 그대로, 불일치만 기록 | **도입 초기**(오탐률 측정) |
| `enforce` | 불인정 대상 제거 | 정식 운영 |

- 위반 처리: 기본은 **대상 제거 + 로그 + 위반 점수**. 자동 제재(킥·밴)는 하지 않는다. 임계 초과 시 `MARKET_ABUSE_SUSPECT`와 같은 방식으로 **운영자 검토용 의심 플래그**를 올린다(명세 12장 기조: 수배는 상태, 제재는 운영자 조치, 오탐 처벌 금지).
- 위반 점수는 시간에 따라 감쇠하고, 정상 경계 판정에서는 누적되지 않도록 허용 오차를 둔다.

#### 2.6.4 설정(`guard.melee`)

```yaml
guard_melee:
  mode: log_only            # off | log_only | enforce
  tick_tolerance: 2         # delay 하한 허용 오차(틱)
  delay_window_ticks: 10    # delay 이후 허용 대기 시간(틱)
  range_tolerance: 0.5      # 블록
  angle_tolerance_deg: 10
  latency_comp_ms: 150      # 0이면 지연 보상 끔
  require_los: true
  max_targets_cap: 8        # 무기별 설정이 더 작으면 그 값
  suspect_threshold: 5      # 위반 점수 (시간당 감쇠)
  apply_to: [pve, pvp, boss]   # 범위별 강도 분리 가능
```

(수치는 모두 [제안]이며 실측 후 확정)

#### 2.6.5 구현 방식 후보

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. LR 포크 패치 | LR의 공격 처리 클래스에서 대상 목록을 서버 재계산 결과와 교집합 | 가장 단순·정확, 업스트림 PR 가능 | 수정 코드는 **GPL 소스 제공** 의무, 포크 유지보수 |
| B. 믹스인 | 코어 모드가 LR 공격 처리 지점(`postAttack` 등)을 후킹해 목록 교체 | LR 소스를 수정하지 않음 | 코어가 LR 내부 구조에 결합(업데이트에 취약), 라이선스 결합 범위 검토 필요 |
| C. 피해 이벤트 사후 검증 | 바닐라/NeoForge 피해 이벤트에서 공격자의 근접 공격 여부를 보고 대상 적합성을 검증 | LR 코드 비의존에 가까움 | 공격 컨텍스트(동작·콤보)를 알기 어렵고 검증 정밀도 낮음 |

- **권장 순서:** ① LR 저작자에게 서버 측 검증 개선(또는 훅 이벤트 추가)을 문의 → ② 불가하면 A 또는 B로 구현. 코어 모드를 LR 코드와 독립시키는 원칙(`mod-license-survey.md`)과 충돌하므로 **B를 택하면 코어 모드 라이선스 범위를 재검토**한다. C는 보조 수단으로만 쓴다.
- 결정은 C0 스파이크(LR 소스에서 `CPrepareMeleeAttack` 처리와 후킹 지점 확인)에서 한다.

#### 2.6.5.1 다른 모듈에 제공하는 이벤트

- 검증을 통과한 타격만 `ValidatedMeleeHit(event_id, attacker_uuid, target_id, weapon_serial, action, combo, tick)` 이벤트로 내보낸다. 보스 기여도·랭킹·도감·칭호 조건은 **이 이벤트만** 입력으로 쓴다(미검증 타격으로 보상이 발생하지 않게).
- `event_id`로 멱등성 보장(14.2장).

#### 2.6.6 범위 밖

- TaCZ 총알은 서버 엔티티(`EntityKineticBullet`)로 처리되므로 이 모듈의 대상이 아니다(총기 피해 상한은 명세 10.2장).
- 근접 피해량·히트박스 값 자체의 조정은 데이터(무기 JSON)에서 한다.

#### 2.6.7 검수 항목

- [ ] 정상 클라이언트(핑 150ms 내외)의 경계 타격이 `enforce`에서도 인정된다(오탐 비율 측정).
- [ ] 원뿔 각도 밖 대상을 지정한 변조 패킷이 피해 0으로 처리된다.
- [ ] 벽 뒤 대상을 지정한 변조 패킷이 `require_los`에서 거부된다.
- [ ] `delay` 이전/허용 시간창 이후에 도착한 패킷이 폐기된다.
- [ ] 한 패킷에 과다 대상을 담은 경우 상한 초과분이 제거된다.
- [ ] 위반 점수가 임계 초과 시 의심 플래그만 올라가고 자동 제재가 없다.
- [ ] `ValidatedMeleeHit`만 보스 기여도·랭킹 입력으로 쓰인다.
- [ ] 서버 재계산 추가 비용으로 TPS가 영향받지 않는다(다수 플레이어 동시 공격 부하 시험).

## 3. 조리 규격 — `cooking` (D-001 반영)

### 3.1 개념

판정을 없앤 대신, 서버가 정하는 **조리 진행 시간**과 **쿨타임**으로 요리 속도를 제어한다. 모든 시간은 **서버 시간**(틱/타임스탬프) 기준이며 클라이언트 입력은 "시작/수령 요청"일 뿐이다.

**확정(D-003):**
- **조리 시간** `cook_time_sec`: 시작부터 완료까지의 진행 시간(레시피별).
- **쿨타임**: **플레이어 단위**. 플레이어마다 `cooldown_until` 하나를 두고, 이 시각 전에는 새 조리를 시작할 수 없다. 레시피는 자신이 유발하는 쿨타임 길이(`cooldown_sec`)를 가진다. 조리대·레시피 단위 쿨타임은 두지 않는다.
- 쿨타임 시작 시점 `cooldown_starts_at: start | ready` 는 설정값이며 기본값은 `start` **[제안]**. 두 값의 관계(`cook_time_sec`와 `cooldown_sec`)는 G3 직업 수익 시뮬레이션에서 조정한다.
- 동시 진행 작업 수와 큐 길이의 상한은 설정값이다(기본 [제안]: 동시 1개, 완료 대기 큐 N개).

### 3.2 `CookJob` 상태 머신

```text
REQUESTED → (검증) → STARTED → READY → CLAIMED
                │                 │
              REJECTED         EXPIRED/CANCELED
```

| 단계 | 서버 처리 |
|---|---|
| REQUESTED | 요리사 직업·레벨·레시피 화이트리스트·쿨타임·조리대 상태 검증 |
| STARTED | **재료를 1회만 차감**하고 작업 레코드를 저장(`job_id`, `started_at`, `ready_at`) |
| READY | `ready_at` 도달 시 완료(오프라인 중에도 서버 시간 기준) |
| CLAIMED | 결과 지급 **1회**. 인벤토리가 가득 차면 보관함으로 이전 |
| CANCELED | 시작 전 취소는 전액 환급, 시작 후 정책은 설정(`refund_ratio`) |

- 모든 상태 전이에 `event_id`를 부여해 **중복 클릭·재접속·크래시에도 차감 1회, 지급 1회**를 보장한다.
- 작업 레코드는 DB에 저장하고, 서버 재시작 후 이어서 진행한다.
- **오프라인 누적 생산 금지**(명세 5.1·5.5장 정신 유지): 동시에 진행 가능한 작업 수와 큐 길이에 상한을 둔다.

### 3.3 레시피 데이터 필드

```text
cook_recipe = { id, required_job, min_level, station,
                inputs[{item, count}], outputs[{item, count}],
                cook_time_sec, cooldown_sec,        # 쿨타임은 항상 플레이어 단위
                sell_price_ref, xp }
```

### 3.4 품질 — B안 확정 (D-004)

판정이 사라졌으므로 품질은 **무작위가 아니라 결정적**으로 정한다.

```text
quality_tier = tier_of(min(job_level_band, tool_tier_cap))
```

- 입력: 요리사 직업 레벨 구간과 식칼/프라이팬 티어. 낮은 쪽이 상한(캡)이 된다.
- 출력: 품질 등급(예: 일반 / 좋음 / 우수 — 등급 수는 [제안]) → **판매가 배수, 경험치 배수, 음식 효과 배수**.
- 같은 조건이면 항상 같은 품질이므로, 이후 요리 결과 분쟁·검증이 쉽고 G3 시뮬레이션이 단순해진다.
- 등급 경계 레벨, 배수 값은 설정 파일(`cooking.quality`)로 관리하며 수치는 G3에서 확정한다. 품질은 결과 아이템에 `quality` 데이터 컴포넌트로 기록한다.
- 명세 5.3장의 "실패 시 일부 재료 환급 / 저품질 생성 완화책"은 판정과 함께 **삭제**된다(실패 개념 없음).

### 3.5 서드파티 조리 모드와의 관계 — 결정 규칙 (D-005)

조리 블록(화로·웍·냄비·도마 등)의 **모션·애니메이션·모델·소리 같은 연출을 코어 제어 아래에서도 재사용할 수 있는지**로 방식을 정한다.

| 방식 | 조건 | 동작 |
|---|---|---|
| **모드 B — 코어 제어(우선)** | 코어가 `CookJob`으로 시작/진행/완료를 통제하면서도 서드파티 블록의 연출을 쓸 수 있음 | 코어가 시작·완료·재료 차감·지급을 결정하고, 서드파티 블록은 **연출만 담당**. 서드파티의 자체 조리 진행은 무시하거나 끈다 |
| **모드 A — 서드파티 방식(대체)** | 연출을 분리할 수 없어, 코어 제어 시 연출이 깨지거나 대체 UI를 새로 만들어야 함 | 서드파티 블록의 조리 흐름을 그대로 쓰고, **최소 방어층**만 얹는다(아래) |

**모드 A의 최소 방어층:** ① 레시피 필터로 허용 레시피만 남김(`guard.recipe`), ② 결과 수령 시점 검증(`guard.craft`): 요리사 직업·최소 레벨·**플레이어 쿨타임**(`cooldown_until`) 확인, ③ 수령 시 품질 컴포넌트 부여, ④ 자동화 입력(호퍼 등) 차단, ⑤ 로그. 재료 1회 소비는 서드파티 모드의 동작에 맡기되 G1 X6(복제·우회)로 검증한다.

- **판정 절차:** G1 4.4절의 "연출 재사용 가능성" 항목 결과로 방식을 정한다. 불확실하면 모드 A로 시작해 C4 이후 모드 B로 승급할 수 있게 `cooking` 인터페이스를 분리해 둔다.
- 모드 A에서는 쿨타임을 **시작 시점이 아니라 수령 시점**에 강제할 수밖에 없는 경우가 있다. 이 경우 `cooldown_starts_at` 은 `ready`로 고정되며, 차이를 G3 수익 계산에 반영한다.
- Farmer's Delight / Kaleidoscope Cookery(+ 호환 모드) 병행 여부는 G1의 A/B/C 비교로 결정하며, 어느 안에서든 위 두 방식이 모두 동작해야 한다.

## 4. 설정·로그·저장

- **설정:** 단일 설정 디렉터리(예: `config/economycore/`)에 `recipes.whitelist`, `cooking.recipes`, `locklist`, `command.policy`. 핫리로드 지원.
- **감사 로그:** `CRAFT_DENIED`, `RECIPE_FILTERED`, `COMMAND_DENIED`, `IDENTITY_DUP`, `COOK_*` 상태 전이. 필드는 명세 12.3장 증거 규격을 따른다.
- **저장:** 코어 단계에서는 SQLite(WAL)로 시작해 PostgreSQL 전환이 가능하도록 저장소 인터페이스를 분리한다(명세 2.1장 권고 승계). 월드 변경은 메인 스레드, DB 쓰기는 비동기 큐 + 재처리(명세 14.2장).

| 단계 | 내용 | 완료 조건 |
|---|---|---|
