## 0. 문서의 목적과 용어

이 문서는 **Minecraft Java 1.21.1 + NeoForge** 서버를 구현할 개발자에게 전달하기 위한 기능 명세다. 이전 Fabric 기반 ‘검 강화·수집 서버’ 아이디어를 새 NeoForge 기획으로 **마이그레이션**한다. **Fabric 모드나 코드를 그대로 호환된다고 가정하지 않는다.**

- **[확정 기획]** 사용자가 직접 명시한 요구. 임의 변경 금지.
- **[승계]** 이전 서버 논의에서 계속 가져오는 사항. 현재 플랫폼/범위에 맞추어 재검토 필요.
- **[제안]** 구현을 구체화하기 위해 추가한 규칙·수치. 운영자가 조정 또는 확정해야 함.
- **[검증]** 모드 배포판 존재는 확인했지만 *함께 실행되는지, 상호작용이 요구대로 작동하는지*는 아직 테스트되지 않은 사항.
- **[v0.2]** 2026-11-11 기획 논의에서 추가·변경된 사항. 근거 문서(`docs/…`)를 절마다 표시한다.

`Coin`은 게임 내 **비현금성** 기본 재화다. 실제 현금·유료 확률형 아이템 및 현금 환전은 본 기획 범위에 포함하지 않는다.

## 1. 제품 비전 및 핵심 루프

### 1.1 서버 정체성

- **[확정 기획]** 누구나 검을 강화하며 장비 도감을 채우고 상위 보스에 도전할 수 있는 경제형 RPG 서버.
- **[확정 기획]** 생활 직업은 농부·광부·요리사·어부의 **4개**를 출시 범위로 한다.
- **[승계]** 사냥꾼·벌목꾼 등의 직업 아이디어는 확장 후보로 보관하되 초기 4개 직업의 수익 구조를 먼저 완성한다.
- **[확정 기획]** 장비는 상점/보상/전문 시스템에서 공급되며 일반적인 조합·모루·인챈트 테이블 사용을 제한한다. **요리사의 전용 요리 제작만 예외**로 허용한다.
- **[확정 기획]** 장비 내구도는 무한. 강화 실패 시 저확률 파괴.
- **[확정 기획]** 가구 설치·주택 꾸미기·**가구 뽑기 시스템**은 정식 경제 콘텐츠에 포함한다.
- **[v0.2]** 근접 무기는 `economycore`가 등록한 **신규 아이템**과 **서버 권위 범위 공격**으로 구현하고, 기존 자체 검 강화 모드는 폐기한다(6.1장, `docs/combat-spec.md`, `docs/gearbridge-spec.md`).
- **[v0.2]** 무기는 아키타입 15종 × 티어 6단계(목제~전설) **후보 361종 카탈로그에서 선별**해 채택한다. 시작 무기는 최초 접속 시 목제 무기 중 1개를 고른다(4.3장, `docs/weapon-archetypes-spec.md`, `docs/weapon-catalog.md`, `docs/starter-weapon-spec.md`).
- **[v0.2]** 연출(이펙트)을 먼저 구현하고 모션 제작은 선택 사항으로 둔다. 고등급 강화 무기는 서버 권위 특수 효과를 갖는다(`docs/fx-spec.md`, `docs/special-effects-spec.md`).
- **[v0.2]** 이 서버는 **현금 과금이 없다**(Coin만 사용). 확률형 요소는 법적 쟁점이 아니라 운영·밸런스 문제로 다룬다.

### 1.2 플레이어 루프

`최초 접속 → 닉네임 지정 → 직업 선택 → 시작 무기 선택(목제 6종 중 1) → 직업 활동 → 생산물 판매/유저 납품 → Coin 획득 → 장비/강화석/인챈트/탄약 구매 → 강화 → 도감·칭호 진행 → 보스 도전 → 상급 재료 획득 → 더 높은 강화`.

병행 루프: `Coin 수입 → 주택/농지 확보 → 가구 상점·가구 뽑기 → 집 꾸미기 → 전시/방문/거래 → 가구 회수·중복 조각 교환 → 주택 확장/유지 비용`.

서버의 모든 재화 생성 경로에는, 서비스 유지에 필요한 재화 소모 경로와 제어 가능한 공급 제한이 짝을 이루어야 한다.

### 1.3 설계 원칙

1. 직업은 **경제적 특화**이지 전투 클래스가 아니다. 검 강화·보스 진입을 직업으로 막지 않는다.
2. **[v0.2]** 장비 시스템은 `economycore` 안의 **장비 계층**(`gear`·`combat`·`fx`)으로 직접 구현하고, 경제 서비스와는 `GearBridge` 인터페이스로만 연결한다(기존 자체 검 강화 모드는 폐기).
3. 일반적인 사냥·생활·채집은 솔로 플레이 가능; 레이드형 보스에 한해 파티 이점 허용.
4. 서버가 모든 거래·보상·확률·권한을 판정한다. 클라이언트 클릭은 **요청**일 뿐 결과를 결정하지 않는다.
5. 데이터를 복구 가능하게 저장하고, 결제/아이템 증감은 **중복 실행 방지와 감사 로그**를 갖춘다.
6. ‘모드가 1.21.1 NeoForge용으로 배포됨’과 ‘우리 서버 모드 조합에서 정상 동작함’은 별도 판단한다.
7. **[v0.2]** 서드파티 모드는 **콘텐츠 공급자**이고, 제작 제한·내구도·복제 방지·피해 계산 같은 **통제는 코어 모드(`economycore`)가 담당**한다(`docs/server-core-mod-spec.md`).

- 현금 과금이 없으므로 NC 조건은 유지되며, 후원·광고·판매가 생기면 전 모드의 라이선스를 재검토한다.

**권고 가구 조합:** 출시 초기에는 **Another Furniture 1종**을 고정하고, 가구 가짓수가 부족하면 **Handcrafted**를 추가한다. **Refurbished**는 기능성 블록(저장/기계 등)을 제한하지 않으면 경제 우회로가 생기므로 별도 검증 후 도입한다. 모든 모드를 무조건 한꺼번에 넣지 않는다.

**추가 광물:** 특정 외부 광물 모드의 무조건적 채택보다 **자체 광산 월드의 광석 블록·전리품 테이블·레벨 게이트를 우선 구현**한다. 별도 광물 모드를 도입할 때는 **1.21.1 NeoForge 파일·광석 ID·월드 생성 규칙·중복 광석·강화 재료 변환 방식** 검증 뒤 채택한다. 현재 명세의 ‘추가 광물’은 **필수 기능**이지만 특정 서드파티 모드가 확정된 것은 아니다.

### 2.3 모드 채택 승인 체크리스트

1. 정확한 MC/NeoForge/Java 버전 일치 및 라이브러리 의존성 충족.
2. 라이선스상 모드팩 배포·수정·에셋 이용 조건 확인(특히 TaCZ·LR 에셋, 가구 모델).
3. 클라이언트 2개 이상 + 전용 서버 기동, 접속·설치·상호작용 테스트.
4. 기본 제작법 차단 후 우회 제작/타 모드 작업대/명령어 생성·아이템 복제 가능성 확인.
5. 서버 TPS, 엔티티/청크/스프링클러/가구 렌더링 비용 측정.
6. 모드 업그레이드와 월드 롤백 테스트 및 **버전 고정**.
7. **[v0.2]** 코드/에셋 라이선스 구분, 클라이언트 배포 시 소스 제공(GPL), ND·ARR 에셋의 수정·재배포 금지 준수 확인(`docs/G1-mod-verification-checklist.md` 3.1).

## 3. 게임 규칙 및 제한 시스템

### 3.1 일반 제작·장비 수리 제한 [확정 기획]

- 플레이어 **2×2 인벤토리 제작**, **3×3 작업대**, 모루, 마법 부여대, 대장장이 작업대, 숫돌의 **장비 제작/수리/인챈트 결과 획득**을 차단한다.
- 단순히 블록 클릭만 막지 말 것. **레시피 데이터 제거 + 작업 화면 결과 검증 + 자동화/타 모드 작업대 우회 검증**의 다층 방어 필요. **[v0.2] 코어 모드가 담당**한다: `guard.recipe`(레시피 로드·리로드 시 화이트리스트 필터, 기본 거부), `guard.craft`(결과 슬롯 수령 시점 서버 재검증), `guard.command`(일반 유저의 아이템 생성 명령·크리에이티브 차단).
- 요리사는 전용 `CookingStation`에서만 승인된 요리를 제작한다. 요리 모드의 기본 제작 경로는 직업 권한/서버 레시피 화이트리스트에 맞춰 재배치(조리 제어 방식은 5.3장).
- 채광 원석→재료 전환, 씨앗 구매 등은 전용 상점 또는 직업 작업대(승인 레시피만)로 처리한다.
- 일반 생존용 블록 설치, 침대·상자 사용 등을 어디까지 허용할지는 **설정값과 화이트리스트**로 관리한다. ‘조합 금지’와 ‘건축 금지’를 혼동하지 않는다.
- 기본 인챈트/수리/거래 우회(주민 거래, 몹 장비 드롭 등)는 획득 허용 정책에 통일한다.

### 3.2 장비 내구도 무한 [확정 기획]

- 서버가 인가한 검·곡괭이·괭이·낚싯대·식칼·방어구·기타 장비는 **사용 시 내구도 감소 없음**. 필요 시 원래 모드가 요구하는 내구도 이벤트를 어댑터에서 차단한다.
- **수분/충전량, 탄약, 일회용 소모품**은 내구도와 다른 리소스다. 무한 내구도가 무한 탄약/물/재료가 되지 않게 구분한다.
- 고장(내구도 0) 대신 **강화 실패 시 파괴**만 장비 소멸 원인으로 삼는다(사망 드롭과 운영자 회수는 별도 정책).
- **[v0.2]** 코어가 발급하는 장비에는 `unbreakable` 컴포넌트를 부여하고 `guard.durability`가 내구도 감소 호출을 차단한다. 자체 근접 무기(`combat`)에는 내구도 소모 개념이 없다(`docs/server-core-mod-spec.md` 2.3).

### 3.3 사용자 인터페이스 [승계 + 제안]

- 메인 메뉴 키(기본 `M`, 리맵 가능): `내 정보 / 직업 / 강화 / 도감 / 상점 / 거래·의뢰 / 주택·가구 / 칭호 / 가이드 / 워프`.
- HUD: 작은 상태 바(직업/직업 XP/재화/수배 상태), 우측 축소형 상태창(온라인 인원·서버 시계); **크리에이티브에서는 숨김**.
- 운영자 메뉴: `/관리자` → 칭호·경제·상점·재고·범죄 로그·토지·보스·확률 설정·서버 공지.
- UI를 클라이언트에서만 가리고 서버 검증이 빠지는 방식은 금지.
- **[v0.2]** 화면 구성은 `docs/g5-wireframes.md`·`docs/g5-wireframes-2.md`(약 50개 화면)를 기준으로 한다. 공격 쿨다운은 **서버 쿨다운을 시각화**해 표시하고(바닐라 쿨다운 대체), 모든 확정 요청은 `request_id`로 멱등 처리한다. UI 구현 방식(서버 메뉴 vs 커스텀 화면+패킷)은 미확정.

## 4. 계정·닉네임·직업 진입

### 4.1 최초 접속 닉네임 [확정 기획]

- UUID가 계정의 영구 키이고 **닉네임은 표시명**이다. 마인크래프트 실제 계정명/UUID를 변경하지 않는다.
- 최초 접속에서 닉네임 설정 UI 표시. 중복/비속어/관리자 사칭/서식 제어 문자/길이(권장 2~12자)를 서버 검사한다.
- 채팅·탭·이름표·거래소·수배 로그에 동일 표시명을 적용한다. 표시 순서는 `[칭호] 닉네임`; 길이 제한과 가독성 옵션 제공.
- 닉네임 변경 허용 여부, 쿨타임 및 수수료는 **운영 정책으로 조절**. 감사 로그는 변경 전후 이름+UUID 보존.
- 로그인/닉네임 UI 취소 시 외부 인터랙션을 제한하되, 재접속 시 이어서 설정 가능.

### 4.2 직업 선택 및 변경

- 출시 직업: 농부/광부/요리사/어부 중 **1개 활성 직업**.
- 직업 레벨·XP는 해당 직업별로 저장. 변경 시 과거 직업 진행도를 보존할지는 **제안: 보존 + 변경 수수료/쿨타임**.
- 직업 도구 지급 시 **소유자 UUID/직업/단계** 기록. 도구 복제·무제한 재지급 차단.
- 직업 도구의 강화는 **전투 검 강화와 분리**. 직업 도구는 일반 강화 도감에 넣지 않는다.
- 기존 ‘일반 XP 폐기→직업 XP 통합’ 방향 승계. 바닐라 XP가 인챈트 우회·보상 중복에 사용되지 않도록 통일.

### 4.3 시작 무기 선택 [v0.2 결정] (`docs/starter-weapon-spec.md`)

- **흐름:** 최초 접속 → 닉네임 → 직업 → **시작 무기 선택** → 지급. UI를 닫아도 재접속 시 이어서 진행.
- **후보:** 입문 친화적인 6종(한손검·단검·쌍검·대검·창·도끼)의 **목제(T0) 무기**. 선택 전 연습장(허수아비)에서 임시 대여 무기로 체험할 수 있으며 체험 결과는 경제·보상·랭킹에 반영하지 않는다.
- **규칙(제안):** 계정당 1회 선택, **획득 시 귀속**(거래 불가), 선택 후 24시간 안에 1회 무료 교체(이전 `serial`은 파괴 처리), 목제 → 철/청동으로 분기 진화. 나머지 9개 아키타입은 상점·진화로 해금.
- **서버 처리:** `starter_claims`로 1회 발급을 보장하고(`request_id` 멱등), 인벤토리 가득·서버 종료에도 1회 발급 ↔ 1개 지급. 시작 무기는 무료이며 Coin 발행 경로가 아니다.

## 5. 네 가지 직업 상세

### 5.1 농부 [확정 기획]

**핵심 루프:** 씨앗/도구 구매 → 공용 경작지 이용 또는 경작지 매입 → 파종/급수/수확 → 수확물 판매·요리사 납품 → 직업 레벨/도구 강화.

**토지 유형**

| 유형 | 소유권 | 파종·수확 | 경제적 역할 |
|---|---|---|---|
| 공용 경작지 | 서버 | 이용 규칙에 따른 이용자 | 진입장벽 낮음, 이용 기록/절도 판정 |
| 개인 구매 경작지 | 구매자 UUID | 소유자 및 허가받은 사람 | 토지 구매비·확장비 발생 |
| 공동 작업 경작지 [제안] | 그룹 계약 | 권한자만 | 협업·의뢰 연동 |

**급수:** `물뿌리개` 아이템에 물 저장(서버 측 충전량). 스프링클러를 설치하면 **정확히 중심 포함 X/Z 각 ±2칸 = 5×5(25블록)** 농지에 작용. 스프링클러는 **물뿌리개로만 충전**한다. 물 소모량/사용 주기/최대 저장량은 설정 파일 관리. 청크 언로드 때는 자동 급수가 중단되고, 재접속 시 **누적 오프라인 생산 무한 지급 금지**. 액체 배관이나 양동이 직접 충전은 허용 여부를 명시적으로 제한한다.

**도구 진화:** 괭이 `나무→돌→철→금→다이아몬드→네더라이트` 단계를 진행한 뒤 **낫**으로 진화한다. 단계별 성공률/재료/비용 표로 설정. 낫 공격 시 서버가 계산한 전방 부채꼴 또는 사각 범위 안에서 **성숙한 작물만** 일괄 수확. 수확 전 좌표마다 권한·경작지 소유·서버 수확량 계산을 검증한다. 부가 효과가 타인 작물을 자동 수확하도록 허용하지 않는다.

**절도/수배:** 공용 경작지에서 다른 이용자에게 점유 또는 예약된 작물 수확 시 사건 로그 생성. 운영 규칙에 따라 `경고→수배 후보→적발 시 제재`. 무조건 자동 처벌하지 않고 **권리 정보와 증거**가 있는 경우에만 제재.

**모드 처리:** 기존 Sprinkler 모드는 범위/충전 규칙이 다름. 이 서버의 스프링클러/물뿌리개/낫/경작지 연동은 **자체 모드로 구현**할 것을 우선한다. 제3자 모드의 자동 수확·재파종은 수익 밸런스 확인 전 사용하지 않는다.

### 5.2 광부 [확정 기획]

**핵심 루프:** 광산 입장 → 광물 채굴 → 일반 광물 판매/상급 광물·강화석 획득 → 곡괭이 단계 강화 → 고등급 광산 개방.

- 곡괭이 단계가 올라갈수록 고부가가치 광물 채굴 가능. 단계와 광물 채굴 권한은 개별 등록 ID로 판단한다.
- 광산은 `일반/심층/희귀/최상급` 등급(등급 수 제안)과 별도 재생 주기/입장 조건·자원 풀을 갖는다.
- 별도 **광산 전용 차원 또는 리셋 가능 구역** 사용을 권장. 일반 주거 월드의 광석 생성으로 경제를 통제하지 않는다.
- 강화석은 낮은 확률로 채굴 보상에 추가 지급. **광산 티어 + 광부 레벨**에 따라 고급 재료 확률이 높아짐. 재료 직접 드롭과 광물 판매 Coin 지급을 혼동하지 않는다.
- 드롭 판정은 매 블록 `event_id + block_pos + world_id + player_uuid` 기준 한 번만. 설치한 광석 재채굴, 피스톤/폭발/실크터치, 리젠 악용으로 보상 중복 금지.
- 추가 광석은 `ResourceLocation` 기반 자체 블록+전리품 테이블 방식으로 최소 구현하고, 아트/월드생성 비용에 따라 외부 광물 모드를 검토한다.
- 상급 곡괭이, 보스 재료, 상급 강화석을 상위 채광 루프와 접목하는 기존 계획을 승계.

### 5.3 요리사 [확정 기획]

**핵심 루프:** 요리사 전직 → 전용 식칼 지급 → 재료 구매/유저 납품 수령 → 전용 프라이팬/조리대 사용 → 조리 시간·쿨타임 → 음식 판매·의뢰 납품.

- 요리 모드는 **G1에서 비교 결정**한다(Farmer's Delight 단독 / Kaleidoscope Cookery 단독 / 병행, 2.2장). 기본 제작대 우회는 불허하고 **요리사 전용 조리 흐름** 및 레시피 화이트리스트로 연결한다.
- 직업 레벨별 요리 레시피 해금. 요리 레시피는 `필요 레벨/입력 재료/수량/조리 시간/쿨타임/결과물/판매 단가`로 데이터화.
- **[v0.2 결정] 타이밍 판정(Perfect/Good/Fail)은 폐지**한다. 대신 레시피별 **조리 시간**과 **플레이어 단위 쿨타임**(플레이어마다 `cooldown_until` 하나, 시작 시점 기준 [제안])으로 속도를 제어한다. 모든 시간은 서버 시간이며 클라이언트 입력은 시작/수령 요청일 뿐이다.
- 실제 재료 소비는 제작 시작/완료 흐름에서 **한 번** 처리한다. 창 닫기·서버 충돌·재접속 시 복제나 재료 손실이 없도록 작업 트랜잭션 저장.
- **[v0.2 결정] 품질은 결정적 보정(B안)**: `quality_tier = tier_of(min(직업 레벨 구간, 도구 티어 캡))`로 판매가·경험치·음식 효과 배수를 정한다(무작위 없음, 실패 개념 없음). 등급 수·배수는 설정값이며 G3에서 확정한다.
- **[v0.2] 조리 제어 방식(D-005):** 코어가 `CookJob`(시작→진행→수령, 재료 1회 차감, 작업 DB 저장)으로 통제하면서도 서드파티 블록의 연출을 재사용할 수 있으면 **코어 제어(모드 B)**, 불가능하면 **서드파티 블록 방식(모드 A)** + 최소 방어층(레시피 필터·수령 시점 직업/쿨타임/품질 검증·자동화 입력 차단)을 쓴다(`docs/server-core-mod-spec.md` 3장).
- 직업용 식칼/프라이팬 강화는 직업 장비 시스템에 속한다. 프라이팬으로 전투 검을 대체할 수 없음(전투 수치 분리).

### 5.4 어부 [확정 기획]

**핵심 루프:** 어종 탐색 → 낚시 도구 성장 → 타이밍 판정 → 어획품 납품 → 희귀 어종 수집/판매.

- **Aquaculture 2 필수**. 해당 모드의 생물군계별 물고기·낚싯대/미끼 시스템 활용.
- 낚시 성공 시 추가 **서버 판정 미니게임**: 물고기 입질 후 지정된 시간창에 우클릭. 네트워크 지연 허용·자동 클릭 탐지·게임패드/접근성 고려.
- 어종별 난이도·레벨 제한·보상·판매 기준가·수요를 별도 데이터로 정의.
- 어부 레벨은 상위 어장/미끼/낚싯대 접근과 희귀 어획 확률에 영향. 희귀어 무한 리스폰/무제한 판매로 유통량이 폭증하지 않도록 어종별 공급 계수 적용.
- 수확물은 상점에 판매하거나 요리사 의뢰와 연결할 수 있도록 식재료 태그 매핑.
- **[v0.2]** 요리 판정 폐지와 별개로 **낚시 타이밍 판정은 유지**한다. 접근성: 시각·소리 신호, 시간창 완화 옵션, 대체 입력 키.

### 5.5 공통 직업 성장 수치 [제안·설정 가능]

- 레벨 구간: 초기 1~50, 추후 확장. EXP는 직업별 따로 계산.
- 레벨별 해금: 전용 도구 티어, 구역 입장, 제작 레시피, 판매 품목, 부가 확률.
- **비정상 반복 입력 보상 제한:** 동일 좌표 반복 채집, 사용자 설치 자원 재수확, 같은 의뢰 돌려막기, AFK 자동화.
- 직업 변경 쿨타임/수수료, XP 곡선, 판매 가격표는 운영자가 설정 가능.

## 6. 장비 강화·인챈트·도감

### 6.1 장비 계층과 `GearBridge` [확정 기획 / v0.2 개정]

기존 자체 제작 검 강화 모드는 **폐기**한다. 장비는 `economycore` 안의 **장비 계층**(`gear`·`combat`·`fx`)으로 구현하고, 경제 서비스(확률·비용·재화)와는 `GearBridge`로만 연결한다(`docs/gearbridge-spec.md`).

- **식별:** 종류 키 `gear_key = (item_id, def_id)`, 개별 키 `serial`(코어 `guard.identity`, 컴포넌트 `economycore:identity`·`economycore:gear`). **정본은 DB**이고 스택 컴포넌트는 캐시다(불일치 시 DB 기준 복구).
- **아이템:** 카테고리별 신규 아이템(`economycore:gear_sword`·`gear_polearm`·`gear_axe`). 무기 종류는 `def_id`(데이터)이며 코드 없이 추가한다.
- **백엔드:** **바닐라 백엔드(신규 아이템 + 자체 서버 권위 범위 공격)를 먼저 구현**하고, 가능하면 LR 근접 체계로 이식한다(FX5 평가). GearBridge는 `GearBackend`로 추상화한다.

```text
GearBridge.identify(stack) / locate(player, serial)
GearBridge.canEnhance(player, stack, ctx) -> {ok, reason, preview{rates_version, cost, rates}}
GearBridge.beginEnhance(event_id, player_uuid, serial, cost)
GearBridge.commitEnhance(event_id, result: SUCCESS|FAIL_KEEP|DESTROY, new_state) / abortEnhance(event_id, reason)
GearBridge.evolve(event_id, serial, to_def_id, cost)
GearBridge.applyStats(stack) / issue(def_id, owner, source_event_id)
발행 이벤트: GearEnhanced, GearEnhanceFailed, GearDestroyed, GearEvolved, CollectionUnlocked   (입력: ValidatedMeleeHit)
```

- **강화 트랜잭션:** `reserve → resolve → apply`. `serial` 잠금, `request_id` 멱등, 서버 RNG, `rates_version` 기록, DB 커밋 후 스택 적용은 **outbox**로 정확히 1회(적용 실패 시 보관함에 정본 상태로 재발급). 강화석·Coin 소비, 결과, 원장, 도감, 칭호를 하나의 이벤트 흐름으로 연결.
- **스탯:** `base_damage(def, tier, level) = def.base_damage × tier_multiplier[tier] × (1 + k × level)` (k = 0.06 [제안]). 공격자 속성에 의존하지 않고 서버가 직접 계산한다. 강화는 **공격력만** 바꾸고 쿨다운·히트박스·사거리는 티어(진화)에서만 바뀐다.
- **인챈트:** 마법 부여대 금지, **전용 서비스**에서 비용을 내고 부여(바닐라 인챈트 컴포넌트 사용, 종류·레벨·중복 제한·제거·교체비·직업별 제한은 데이터).
- **진화:** `def_id` 교체(`serial` 유지). 강화 단계는 `carry_over_ratio`(기본 0.5, 내림)만큼 이월 [제안]. 진화 트리는 분기 최대 2, 노드 깊이 3~4단계(시작 단계 포함 T0→T5).
- **귀속:** 일반·희귀 장비(T1~T3)는 거래 가능(시리얼 유지, 수수료 소각), 영웅 이상(T4~T5)·진화 최종형·보스 재료 장비는 획득 시 귀속 [제안].
- **직업 장비는 도감 제외**. 검(근접 무기)을 1차 도감 대상으로 하고 방어구·활·기타는 확장 범위.

#### 6.1.1 근접 전투 `combat` [v0.2] (`docs/combat-spec.md`)

- **서버 권위:** 클라이언트는 공격 **의도**(`C2SAttackIntent`)만 보내고, 서버가 쿨다운·콤보·대상 선정(원뿔/OBB/부채꼴 + 시선 차폐 검사)·피해·넉백을 계산한다. LR 방식의 클라이언트 대상 선정 신뢰 문제가 구조적으로 사라진다.
- **피해:** 바닐라 피해 경로를 사용해 방어구·인챈트·피해 이벤트와 호환. 크리티컬은 바닐라 점프 크리티컬 조건(×1.5, 도끼 1.8), 힘 효과 등 바닐라 보정은 기본 미적용. 이 아이템을 든 상태의 바닐라 공격·휩쓸기·블록 채굴은 차단.
- **PvP는 기본 끔**(지정 아레나·이벤트 구역에서만 허용 [제안]).
- **아키타입 15종:** 한손검·단검·쌍검·대검·창·도끼·레이피어·곡도·카타나·해머·메이스·할버드·쌍단검·쌍도끼·대낫(전투용). **같은 티어에서 단일 대상 지속 DPS를 비슷하게**(일반 9.7 ±5%, 광역 -10%) 맞추고 차이는 사거리·광역·기동·유틸·연출에서 만든다(`docs/weapon-archetypes-spec.md`).
- **쌍검(양손) 방식 A:** 쌍검 1세트 = 아이템 1개(`serial` 1개), 콤보가 좌·우 손을 번갈아 공격, 쌍검을 든 동안 오프핸드 사용을 서버가 차단(`hands: 2`).
- **카탈로그:** 아키타입 15 × 테마 23 + 고유 16 = **후보 361종**을 생성·DPS 검증하고(`docs/weapon-catalog.md`) **채택할 것만 선별**한다. 전설 후보가 많으므로 아키타입당 1~2개와 고유 무기 위주로 채택하길 권한다.

#### 6.1.2 이펙트·특수 효과 [v0.2] (`docs/fx-spec.md`, `docs/special-effects-spec.md`)

- **이펙트(`fx`):** 서버 권위 트리거(`GearActionEvent`: 휘두르기·타격·치명타·처치·강화·진화)로 파티클·소리를 서버가 전송하고, 화면 흔들림·궤적 리본 등 클라이언트 효과는 2단계로 둔다. 정의는 JSON+핫리로드, 파티클·소리 예산과 상세도 옵션(접근성)을 둔다. 모든 에셋은 자체 제작 또는 허락받은 것만 사용한다.
- **특수 효과(게임플레이):** 강화 단계가 해금한다(T3 +10에 1개, T4 +10·+15에 2개, T5 +5·+10·+15에 3개 + +20 각성). 서버 RNG·내부 쿨다운·효과 연쇄 금지·보스 감쇠를 적용하고 **효과 기대 DPS는 기본의 15% 이내**로 제한한다(`Effect_Packs` 시트: 전설 최대 14.3%). 테마 효과 팩 6종(불꽃·서리·번개·성광·맹독·그림자).

### 6.2 강화 위험 관리 [제안]

- 단계별 확률·재료·Coin 비용·파괴 확률을 데이터로 운영. **구체적인 확률 수치는 아직 확정되지 않음**.
- 성공률/실패율/파괴율 합은 각 단계별 100%. 동일 장비에 동시 강화 요청이 들어오면 단일 결과만 생성.
- 파괴 시 아이템 소멸, 인챈트 등 부속 정보 처리, 도감 보유 기록 유지 여부를 명시: **제안: 도감 업적은 유지**, 실물 보유는 사라짐.
- 확률 변경 시 `rates_version`을 기록하여 사후 감사 가능하게 구성.
- **[v0.2·제안] 파괴 완화 장치(G3 `Enhance_Mitigation` 비교 결과):** 장비를 잃는 손실감을 실제로 줄이는 것은 **보호권**(파괴를 유지로 전환하는 소모품)뿐이다(+12에서 소멸 확률 46%→10%). 추천 조합: **안전 구간(8단계 미만 파괴 없음) + 보호권(10단계부터, 1,500 Coin 안팎) + 파괴 시 투입 강화비 30% 환급**. 환급·단계 하락·강화 천장 단독은 손실감을 줄이지 못한다. 채택 여부와 가격은 미확정(19장).
- **[v0.2] 난수 시뮬레이션 기준:** 목표 단계 총비용의 **P90 ≤ 평균의 2배**, 목표 단계에서 장비를 한 번 이상 잃는 유저 비율 ≤ 30%를 점검한다(G3 `MonteCarlo`).

### 6.3 도감·보상 [확정 기획]

- `gear_id + enhance_level + evolution_id` 조합별 **최초 달성**을 영구 기록. 동일 아이템 반복 강화로 보상을 중복 지급할 수 없음.
- 범위별 장비 도감(검/방어구/활/기타), 수집률, 티어별 마일스톤, 완료 보상을 구현.
- 마일스톤 보상: Coin 소량, 장식 아이템, 가구 뽑기권, 한정 칭호, 외형 이펙트 등. **직업별 경제 수익을 급격히 높이는 영구 버프는 지양**.
- 이미 획득한 칭호를 장비 파괴 후에도 유지하도록 설계(획득 업적과 현재 착용 장비는 별개).
- **[v0.2]** 도감 키는 `(gear_id, enhance_level, evolution_id)`. 진화 이월·귀속·진화 트리는 6.1장 규칙을 따르고, 도감 달성 보상은 서버가 1회만 지급(`reward_event_id`)한다.

### 6.4 칭호 [확정 기획]

- 운영자는 게임 내에서 칭호의 `생성 / 수정 / 부여 / 회수 / 삭제(비활성화)` 가능.
- 칭호는 접두/접미 표시 정책(기본 `[칭호] 닉네임`), 색상, 설명, 희귀도, 부여 이유, 획득일, 공개 여부를 갖는다.
- 영구 삭제 시 부여 기록을 없애지 말고 비활성화 처리하여 감사 로그 유지.
- 닉네임·칭호 충돌·Tab 표시길이·채팅 악용 색 코드·플레이어 이름 위 렌더링을 클라이언트/서버에서 테스트.
- **[v0.2] 칭호 조건 시스템:** 조건 유형(도감·직업·보스·강화·시즌·이벤트)을 JSON(AND/OR)으로 정의하고 핫리로드한다. `(player_uuid, title_id)` 유니크로 반복 달성에도 1회 지급, 새 칭호 추가 시 **소급 평가**(미리보기 후 실행), 칭호 세트(전체 보유 시 상위 칭호), 숨김 칭호, 장착 슬롯·변경 쿨타임을 지원한다.

### 6.5 치장·소셜 [v0.2 제안] (`docs/cosmetics-social-spec.md`)

- **원칙:** 전투 판정 불변, 뽑기 외에 직접 구매·업적 경로 하나 이상, 삭제 대신 비활성화, 랭킹 보상은 칭호·치장만(Coin 보상 금지).
- **이름 꾸미기:** 서버가 정의한 스타일 ID(색·그라데이션·장식)만 선택 가능(임의 서식 코드 금지, 가독성 검사). 구매는 Coin 소각.
- **프로필 카드:** 직업·도감률·보스 기록·대표 장비(스냅샷)·소개 문구, 공개 설정(공개/친구/비공개).
- **서버 알림·명예의 전당:** 높은 강화 성공·보스 최초 클리어 공지(강화 파괴는 전체 공지하지 않음), 보스 최단 기록(파티 크기·난이도별 분리)과 직업 주간 랭킹, 의심 기록 무효 처리.
- **검 외형·이펙트 치장:** 바닐라 백엔드는 우리 컴포넌트·커스텀 모델, LR 백엔드는 `DisplayId`. fx 스킨은 스탯·도감 키를 바꾸지 않는다.

## 7. 서버 경제와 재화 순환

### 7.1 통화와 원장 [확정 기획 + 제안]

- 기본 화폐 `Coin`. 별도의 유료 화폐를 기본 설계에서 만들지 않는다.
- **재화 생성:** 직업 수확물 NPC 판매, 일회성 업적/퀘스트 보상, 관리자가 공시한 이벤트 보상.
- **재화 이동:** 유저 간 거래·의뢰 보수·경매; 이는 **재화 소모가 아님**.
- **재화 소멸(싱크):** 강화 비용·인챈트 비용·상점 구매비·거래 수수료·토지 구입/확장/유지·가구 뽑기/직접 구매·워프 비용·일부 편의 서비스·공식 경매 수수료. **[v0.2 추가]** 직업 부대비용(씨앗·입장·연료·미끼)·요리 재료비(NPC 구매)·강화 보호권·이름 스타일/칭호 구매·직업·닉네임 변경 수수료·시작 무기 진화.
- 모든 증감은 `ledger_entries`에 `출처/대상/금액/사유/참조 ID/시간` 기록. 계좌 잔액 음수 불가.

### 7.2 변동 시장경제 [확정 기획]

**목표:** 특정 직업의 반복 생산으로 NPC 판매 가격이 과도하게 유지되는 것을 방지한다. 다만 초기/저인구 서버에서 가격이 붕괴하지 않도록 하한선을 둔다.

**제안 가격식(일일 계산 또는 일정 간격 배치):**

```text
Q = EMA(최근 1~7일 NPC 구매 수량)  # 과잉 판매 지표
D = 운영자가 설정한 목표 매입량(품목 또는 카테고리별)
P_sell = clamp(P_base * (D / max(Q, Q_min)) ^ alpha, P_floor, P_cap)
```

- `alpha`, 가격 변동 상하한, 최소 보장가, 기준 수요량은 품목별 설정.
- 급격한 가격 급락 방지: **하루 변동폭 상한**(예: ±10%, 제안).
- **정산 시점에 화면에 고지한 가격을 단기간 보장**하되 한꺼번에 대량 판매 시 수량별 재계산/하루 판매 한도를 둘 수 있다.
- 보유 물량이 아닌 *실제 NPC 매도 체결*에만 공급량을 합산; 관리자가 유통 통계를 검토.
- 어종/광석/농작물은 품목별 독립 가격+직업별 공급 균형을 유지. 요리는 **원재료 가격 대비 마진**이 나도록 레시피 원가를 계산하고 상점 식재료 구매를 비용에 포함.
- 경제 대시보드: `신규 Coin 발행량, 소각량, 총 통화량, 상위 품목 판매량, 직업별 순수익/시간, 평균 장비 강화 소비, 거래량, 가구 뽑기 지출`.

### 7.3 상점 [확정 기획]

- 장비, 직업 도구, 식재료/씨앗, 강화 재료, 인챈트, 총기·탄약, 인테리어 가구, 생활 편의 서비스를 카테고리별 판매.
- 구매 수량 지정, 소지 한도·재고 한도·거래 제한 안내.
- 판매·구매는 원자적 처리: 재화 차감 실패 시 아이템 지급 금지, 지급 실패 시 차감 롤백.
- 상점 가격 변경은 관리자 검토·버전 기록. NPC 판매가와 NPC 구매가 사이 마진 관리로 무한 차익거래 방지.

### 7.4 기존 경제 계획과의 접점 [승계]

- 출석 보상(이전 안: **30분×4회, 총 2시간**)은 초기 유동성 조절을 위해 작은 비율로 설계. 지급 상한·일일 리셋·AFK 악용 방지.
- 사망 패널티(이전 안: **직업 XP 차감과 일정 시간 획득량 -50%**)는 개발 후 테스트 후보. 레이드 이탈·생활 직업 격차가 심해지면 완화하고, Coin 몰수와 중복 패널티는 지양.
- 방어구 강화·활 강화·오오라·장식용 외형은 확장 범위로 유지.

## 8. 유저 게시판·거래·의뢰

### 8.1 게시판 유형 [확정 기획]

1. **판매 등록:** 아이템/수량/개당가/총가/유효기간. 등록 시 아이템을 **에스크로 보관**.
2. **구매 요청:** 원하는 아이템/수량/지불 상한. 등록 시 Coin을 **에스크로 보관**.
3. **납품 의뢰:** 직업별 물품, 수량, 품질, 납기, 보수, 취소 규칙.
4. **자유 게시판(선택):** 거래와 무관한 게시글, 신고·운영 정책 별도.

### 8.2 거래 절차

`등록 → 보관/보증금 확인 → 공개 → 상대가 수락 → 품목/잔액/권한 재검증 → 물품과 Coin 동시 교환 → 수수료 소각 → 이력 저장 → 알림`.

- 거래 실패·만료·취소 시 에스크로를 정확히 1회 환급. 의뢰 일부 납품 허용 여부는 품목별 설정.
- 집/가구·장비 거래 시 **소유권·시리얼·귀속 조건** 검증. 총기 제한은 10장 참조.
- 가짜 장비·가짜 가구가 위장 등록되지 않도록 item registry, component 데이터 및 태그를 검증.
- 게시판 검색·정렬(가격/종류/직업/남은 시간), 사기 신고, 거래 이력 조회.
- 실사용 수수료(제안): 등록비 또는 거래 완료 2~5% 중 한 방식으로 시작, 데이터로 조정.

## 9. 토지·주택·가구·뽑기 — 정식 경제 콘텐츠

> **이 장은 신규 부가 아이디어가 아니라 출시 대상 기능이다.** 단지 모드를 설치하는 것으로 끝나지 않고, 서버 경제의 명확한 **Coin 소비 경로**로 만든다.

### 9.1 주택/토지

- 플레이어는 `주택 구획(Housing Plot)`을 **구매 또는 임대**하고 소유/이용 권한을 관리한다.
- 주택은 생활 공간+가구 전시 공간. **경작지 구매**와 **주택 구매**는 별도 구역/가격표를 갖는다.
- 토지 구획에는 `plot_id, owner_uuid, world_id, bounds, price, purchased_at, permission, status` 기록.
- 편집 권한: 소유자 / 동거인(허가받은 유저) / 방문자 / 관리자. 방문자는 기본적으로 파괴·수거·창고 열기 불가.
- 소유권 보호는 FTB Chunks 연동 또는 자체 플롯 권한 중 하나의 **권위 원천**을 결정. 둘 다 독립적으로 처리하면 충돌할 위험이 있음.
- 임대라면 기간 만료 직전 안내, 만료 후 **자동 보관함 회수**와 유예 기간. 예고 없는 가구 삭제·토지 몰수 금지.
- **주택 확장 비용**·꾸미기 슬롯·추가 방/층·가구 보관함 확장 비용을 Coin 싱크로 설계.

### 9.2 가구 모드 적용 정책

- **필수:** 실제 1.21.1 NeoForge 배포판이 있는 가구 모드 1종 이상. 기본 후보는 **Another Furniture**.
- `furniture_catalog` 등록 화이트리스트를 통하여 가구 종류·가격·획득 경로(풀/직접 구매)·상호작용 가능 여부·판매 여부를 관리한다. **가구에는 등급(희귀도)을 두지 않는다**(9.3).
- 타 모드 레시피로 뽑기 전용·시즌 한정 가구를 무한 제작할 수 없도록 **가구 조합법 제거 및 우회 작업대 차단**.
- 기본 가구와 뽑기 전용 디자인은 **같은 원본 모델 색상만 바꿀 수 있다고 가정하지 않는다.** 외형 변형에는 별도 에셋/리소스팩/모델 작업 또는 이미 존재하는 다른 가구 ID 필요.
- **기능성 가구(저장·제작·자동화·식량 생성)**는 배치 전에 화이트리스트와 권한 검증을 통과해야 하며, 생산량·인벤토리 기능을 남용할 수 없도록 기능 제한 또는 **장식 전용** 처리.
- 주택에 설치/회수/이동한 가구는 `furniture_instance_id`와 `plot_id`로 추적. 중복 회수·폭발·피스톤·호퍼·청크 언로드를 포함한 무단 복제 방지.

### 9.3 가구 뽑기 [확정 기획 / 세부 수치 제안] — v0.2 개정(등급 없는 균등 풀)

**구매 단위:** `Coin → 가구 뽑기(1회/10회) → 균등 확률 결과 → 가구 인벤토리 → 주택 배치/거래/중복 조각 교환`.

- 뽑기는 **게임 내 Coin만 사용**. 실제 화폐/외부 현금 거래·재판매·환전 금지.
- **[확정 기획] 가구에 등급(희귀도)을 두지 않는다.** 한 풀 안의 모든 가구는 **같은 확률(1/N)** 로 나온다. 가구의 구분은 등급이 아니라 **풀(상시·테마·시즌 한정)과 획득 경로**로 한다.
- **풀(pool):** `pool_id`, `pool_version`, 가구 목록(N종), 1회 가격, 선택 천장 K, 조각 교환 비용 X, 종류(상시/테마/시즌), 유효 기간. **풀 크기 N과 1회 가격이 난이도를 정한다.** 풀 크기는 30~100종 범위를 권장한다 [제안].
- **확률은 UI에 공개**한다: 풀 구성(가구 목록), `각 가구 1/N`, 풀 버전, 선택 천장·조각 규칙, 시행 시점·결과·지급 ID 기록.
- **선택 천장 [제안]:** 유저는 풀에서 **목표 가구(찜) 1개**를 지정할 수 있다. 목표 가구를 얻지 못한 채 누적 뽑기가 `K`회(기본 `K = round(1.5 × N)`)에 도달하면 **목표 가구를 보장 지급**한다. 뽑기로 목표를 얻거나 보장 지급이 일어나면 카운터를 초기화하고, **목표를 바꾸면 카운터가 초기화**된다(확인 팝업으로 고지). 카운터와 남은 횟수는 UI에 항상 표시한다.
- **중복 → 가구 조각 [제안]:** 중복 가구 1개당 **1조각**(풀별 조각). `X`조각(기본 `X = round(0.5 × N)`)을 모으면 **풀 안의 미보유 가구 1개를 지정 교환**할 수 있다. 조각은 거래·외부 현금화 불가.
- **확정 경로 보장:** 선택 천장과 조각 교환으로 **원하는 가구를 얻는 경로가 항상 존재**한다(뽑기 운에만 의존하지 않음). 기본 가구는 9.4의 직접 구매로 항상 얻을 수 있다.
- 10회 구매 할인은 경제 정책으로만 조절(기본 10%); 무한 재구매를 강요하는 미끼형 연출 지양.
- 기능성/성능 가구는 확률상자 전용 보상으로 만들지 않는 것을 권장. **가구는 기본적으로 외형 목적**.
- 뽑기 중 서버 종료, 더블 클릭, 재시도, 인벤토리 꽉 참에도 **Coin 1회 차감 ↔ 결과 1회 지급** 일치. 지급 실패 시 보관함으로 이전.
- **거래:** 상시·테마 풀 가구는 거래 가능, **시즌 한정 가구는 운영 선택**. 거래 시 소유·획득 경로(`source`)를 추적한다.
- **가격 설계 원칙:** 1회 가격은 **고정**하고(초기 후보 560 Coin [제안]) 난이도는 풀 크기로 조절한다. 지정 가구 1종의 기대 비용은 대략 `0.7 × N × 1회 가격`(선택 천장 1.5N + 조각 0.5N 적용 시)이다.

**설계 근거(G3 `Gacha_Flat` 시뮬레이션, N=68·1회 600 Coin·중견 월소득 약 13.3만 Coin 기준, 모든 수치 [제안])**

| 구조 | 지정 가구 평균 | P90 | 최악(상한) | 평균 비용(균등 대비) |
|---|---|---|---|---|
| 균등·천장 없음 | 67.6회 | 154회 | 없음(P99 300) | 1.00 |
| **선택 천장 1.5N + 조각 0.5N (기본 제안)** | **47.9회** | **83회** | 102회 | **0.71** |

- 조각 교환 비용을 낮출수록 꼬리(P90)가 크게 줄어든다(X=0.25N → 평균 37회, X=N → 57회).
- 풀 크기 30~150에서 같은 구조가 평균 비용을 약 30%, P90을 약 45% 줄인다.

#### 9.3.1 가구 풀 구성 예시 [제안]

| 풀 | 구성 예시 | 크기 N(예) | 획득 경로 | 평균 비용(560 Coin, 선택 1.5N+조각 0.5N) | 경제 효과 |
|---|---|---|---|---|---|
| 기본 생활(상점) | 의자·책상·침실 장식 | — | **직접 구매(뽑기 없음)** | 고정가 | 진입용 소액 소각 |
| 상시 풀 | 생활·장식 혼합 | 68 | 뽑기·조각 교환 | 약 2.7만 Coin | 장기 Coin 소각 |
| 농장 테마 풀 | 허수아비·나무 선반·농가 소품 | 30 | 뽑기·조각 | 약 1.2만 Coin | 농부 테마 수요 |
| 광산 테마 풀 | 광물 전시대·광부 램프·작업 소품 | 30 | 뽑기·업적 | 약 1.2만 Coin | 광부 테마 수요 |
| 주방 테마 풀 | 테이블·냄비 장식·조리 가구 | 30 | 뽑기·조각 | 약 1.2만 Coin | 요리사 테마 수요 |
| 바다 테마 풀 | 수족관 장식·그물·항해 소품 | 30 | 뽑기·어부 업적 | 약 1.2만 Coin | 어부 테마 수요 |
| 시즌 한정 풀 | 계절 한정 장식·기념품 | 12~30 | 시즌 뽑기·이벤트 | 약 0.5~1.2만 Coin | 주기적 수요 생성 |

(평균 비용 = 0.7 × N × 560 Coin. 직접 구매 가구와 풀 가구의 가격 관계, 시즌 풀 복각 정책은 운영 결정.)

**중요:** 이 표는 *보상 기획 예시*이며 개별 가구가 해당 모드에 실제로 존재한다는 뜻은 아니다. 개발자는 선택한 가구 모드의 실제 **블록 ID와 사용 가능한 모델**을 확인하여 목록을 확정해야 한다.

### 9.4 주거 확장 콘텐츠 [제안·추가 Coin 소각 경로]

- **가구 직접 구매:** 뽑기 없이 원하는 기본 가구를 고정 가격으로 구매. 장식 진입을 뽑기에 종속시키지 않음.
- **주택 확장:** 면적/설치 가능 가구 수/개별 전시 슬롯 확대. 확장비는 Coin 소각.
- **가구 색상·장식 리폼:** 승인된 모델 변형만 제공. 리폼 비용은 Coin+직업 납품 재료로 설정.
- **수족관/식물 진열/요리 전시관:** 어부의 물고기, 농부의 식물, 요리사의 음식이 장식품 전시 수요로 연결됨. **전시물 회수 시 복제 방지**.
- **트로피 전시:** 보스 클리어 트로피·도감 달성 기념패. 계정 업적 기반 지급으로 중복 Coin 발행 없음.
- **마을 주택가/방문 기능:** 방문·좋아요·스크린샷 공간. **좋아요 수에 따른 무제한 Coin 보상은 금지**(어뷰징 우려).
- **이삿짐 보관:** 이사·구획 만료 시 가구를 계정 보관함으로 이동, 회수 수수료/보관 용량 확장을 설정.
- **외형 편의 상점:** 칭호 테두리·파트클·집 벨소리/문패(리소스 제작 허용 범위 내) 등 공격력을 올리지 않는 장식 서비스.

### 9.5 가구 재화 흐름의 핵심 문제

**가구 뽑기 판매액은 `Coin 소각`**이지만 **유저 간 가구 거래액은 `Coin 이동`**이다. 둘을 ‘재화 소모’로 집계하지 않는다. 운영 대시보드에서 신규 Coin 발행/소각/유저간 이동을 구분한다. 한정 가구를 무한 공급하면 시장이 포화되므로 뽑기 풀 교체·조각 교환·가구 전시 수요를 조절하되, 사용자의 이미 획득한 가구를 임의 삭제해서 공급을 억제하지 않는다.

## 10. 총기 (LR + TaCZ) [확정 기획]

> **[v0.2]** TaCZ와 LR 모두 **공식 1.21.1 NeoForge 빌드**가 있어 비공식 포트·직접 포팅이 필요 없다(TaCZ 1.x LTS 1.2.0, LR `1.21.1` 브랜치). 코드는 GPL-3.0, 에셋은 TaCZ CC BY-NC-ND 4.0·LR ARR이므로 **에셋은 무수정 사용**하고 수정이 필요한 모델·모션은 자체 제작 에셋으로 대체한다(2.2장). 이 서버의 **검은 TaCZ/LR 근접 체계를 쓰지 않는다**(6.1장).

### 10.1 판매 구성

| 분류 | 기본 구성 | 역할 | 밸런스 목표 [제안] |
|---|---|---|---|
| 권총 1종 | 권총 + 전용 탄약 1세트 | 이동·보조 공격 | 낮은 연사·합리적 탄약값 |
| 소총 1종 | 소총 + 전용 탄약 1세트 | 일반 원거리 | 지속 DPS가 검을 압도하지 않도록 |
| 샷건 1종 | 샷건 + 전용 탄약 1세트 | 근거리 폭발 피해 | 거리 감쇠·펠릿 한도 |
| 저격총 1종 | 저격총 + 전용 탄약 1세트 | 장거리 고위력 | 낮은 장탄/비싼 탄약/보스 보정 |

- 총기와 탄약은 **종류별 정확한 Item ID/Ammo ID를 등록한 상점**에서 공급. 다른 탄환 호환 오설정 방지.
- **[승계]** 총기는 강화·스킬 대상에서 제외, 고가 아이템이며 기본적으로 **소유자 귀속·유저 거래 금지**. 탄약 구매형.
- 총기 획득 시 사용자 UUID 부여, 투하/보관/사망 드롭/거래·의뢰 등록/공유창고/핫바 이동 경로에서 귀속을 검증.
- 기존 총기 HUD(탄약/장전 정보), 장전 메커니즘, 종류 구별을 테스트 항목에 포함.

### 10.2 높은 총기 피해량 조정

1. **데이터 레이어 우선:** TaCZ gunpack의 JSON/설정에서 `기본 피해·발사 간격·탄 퍼짐·사거리·장탄·재장전 시간` 조정 가능한지 검사.
2. **서버 피해 보정:** 총알 피해 이벤트를 신뢰성 있게 가로챌 수 있는지 확인. 피해 조정은 **중복 적용되지 않는 단일 위치**에서 처리.
3. **상대별 보정:** PvE 일반 몹, 보스, PvP(허용 시) 피해 상한을 각각 지정. 헤드샷·치명타·다발 펠릿 합산에도 전체 한도를 적용.
4. **경제적 보정:** 총알 종류별 가격·1세트 발수·발사당 비용을 설정해 운용비 발생.
5. **우선 지표:** 동일 장비 성장 단계에서 `총기 DPS/검 DPS`, `보스 클리어 시간`, `탄약 Coin 소모/분`, `유효 사거리`, `생존성` 비교.

**주의:** 단순히 총알 가격만 올리는 것은 높은 순간 폭딜 문제를 해결하지 못한다. **보스 피해 상한 + 발사 수치 + 비용**을 같이 조절한다. TaCZ 1.2.0(LTS)과 LR 1.21.1 브랜치의 버전 매칭·의존성(simplebedrockmodel·player-animation-lib·cloth-config 등)·건팩 업그레이드 오류는 **개발 초기 최우선 테스트 리스크**다. TaCZ 2.x 시리즈(개발 중)로의 전환 시 호환성 변화 가능성을 위험 등록부에 기록한다.

## 11. 보스와 상위 강화 재료 [확정 기획]

- 보스전은 **직업 무관**. 검 강화 진행도가 핵심 진입 준비다.
- 종류/난이도별 보스, 상급 강화 재료 테이블, 클리어 기록, 재도전 쿨타임/입장권/공개 전리품 규칙 지정.
- **[제안]** 보스는 인스턴스/예약 아레나에서 소환, 기본 월드 무작위 등장 제한. 서버 파괴·아이템 드롭 이슈 최소화.
- 보스별 `boss_id, difficulty, min_gear_score, party_size, cooldown, loot_table, weekly_cap` 설정.
- Cataclysm은 후보지만, 모드 자체 전리품의 과도한 무기/방어구가 기존 강화 루프를 우회하면 **드롭 제거 또는 전용 재료로 변환**해야 한다.
- 참여/기여 보상은 서버 권위로 계산, 소환 취소·고의 자살·보스 끌고 나오기·접속 종료 악용 방어.
- 협동을 장려하되 **레이드 이외 콘텐츠는 강제 파티 금지**. 솔로 가능한 단계도 설계.
- **[v0.2]** 보스 기여도·랭킹·도감·칭호 보상은 **서버가 검증한 타격(`ValidatedMeleeHit`)만** 입력으로 쓴다(미검증 타격으로 보상 발생 금지). 보스 효과 감쇠(`boss_scale`)와 제어 효과 제한을 적용한다.

## 12. 범죄·수배·감사 로그 [확정 기획]

### 12.1 기조

- 절도 등 게임 내 위반 행위가 발생하면 **행위·대상·위치·시간·권한 상황·결과를 로그로 남겨**, 운영자가 검토할 수 있게 한다.
- **‘수배’는 게임 상태**, **‘제재’는 운영자 조치**로 구분한다. 정상적 접근을 오탐으로 처벌하지 않는다.
- 개인 신상정보/IP를 필요 이상으로 보관하지 않는다. 로그 열람은 운영 권한 통제.

### 12.2 사건 정의

| 이벤트 | 발생 시점 | 서버 기본 대응 |
|---|---|---|
| `CROP_HARVEST_UNAUTHORIZED` | 예약/소유권 있는 경작지의 타인 수확 | 작물 소유·권한 증거 기록, 정책에 따라 수배 후보 |
| `BLOCK_BREAK_UNAUTHORIZED` | 주택 구획 내 허가 없는 파괴 시도 | 기본 차단 + 시도 기록 |
| `CONTAINER_ACCESS_UNAUTHORIZED` | 남의 창고 접근 시도 | 기본 차단 + 기록 |
| `ITEM_PICKUP_SUSPECT` | 타인 소유 표시된 드롭 줍기 | 맥락 기록, 즉시 제재 금지 |
| `MARKET_ABUSE_SUSPECT` | 순환 거래/아이템 복제 의심 | 의심 플래그/운영 대시보드로 검토 |

### 12.3 증거 규격

`incident_id, actor_uuid, target_uuid, world_id, x, y, z, action, object_id, plot_id, permission_snapshot, event_time, event_result, evidence_json, reviewed_by, disposition`.

- UUID가 기준, 닉네임은 당시 표시값을 스냅샷으로 저장.
- 수배 상태 생성/해제/기한/사유/제재 수위를 관리자 UI에서 관리.
- 억울한 제재 방지를 위한 사건 내역·이의신청 경로 및 로그 보존기간(운영 정책)을 명시.
- 관리자에 의한 수배·벌금·아이템 회수도 별도 변경 이력 기록. **실제 유저끼리 처벌 권한을 무분별하게 부여하지 않음**.

## 13. 확장 가능한 추가 재화 순환 콘텐츠 [제안]

가구/주택과 강화 외에도 과잉 생산을 억제할 ‘선택적 지출’을 만든다.

| 콘텐츠 | 주요 구현 | Coin 소각 방식 | 주의사항 |
|---|---|---|---|
| 개인 창고 확장 | 계정 보관함 슬롯 확장 | 슬롯 구매비 | 초기 기본 보관량은 충분히 제공 |
| NPC 편의 워프 | 상점·광산·낚시터·집 이동 | 저렴한 이용료 | 기본 이동권을 과도하게 제한하지 않음 |
| 장비 외형 스킨 | 파티클·검 외형·오오라 | 구매/리폼비 | 전투 판정·명중 범위 불변 |
| 주택 문패·배너 | 닉네임·칭호 전시 | 제작/등록비 | 금칙어 검열 |
| 보스 트로피 쇼케이스 | 클리어 업적 전시 | 전시장/받침대 구매 | 보상 복제 금지 |
| 직업 납품 계약 | 유저·NPC가 요구 물량 공고 | 등록비·수수료 | 의뢰 보수 자체는 Coin 이동·발행으로 분리 |
| 정기 시장 행사 | 지정 품목 우대/공급 조정 | 참가비/장식 구매 | 과도한 Coin 발행 방지 |
| 가구 색상 리폼 | 합법 모델/텍스처 변형 | 리폼비+재료 | 리소스팩/모드 호환 확인 |

**출시 범위 확정 우선순위:** 가구/주택/가구 뽑기는 **필수**. 기타 선택 확장은 핵심 시스템 안정화 후 단계적 채택.

### 14.2 공통 데이터 규약

- 모든 아이템 종류는 **`namespace:path` ResourceLocation**으로 식별. 사용자에게 표시되는 한글명은 키가 아니다.
- 유니크 장비·가구는 `instance_uuid`를 부여. 외부 모드 NBT/데이터 컴포넌트와 충돌하지 않도록 래퍼 메타데이터 정책 문서화.
- **[v0.2]** 장비의 종류 키는 `(item_id, def_id)`, 개별 키는 `serial`(UUID)이다. 우리 데이터 컴포넌트는 `economycore:` 네임스페이스(`identity`·`gear`)로 분리하고 타 모드의 `CUSTOM_DATA`와 섞지 않는다. 발급은 장부(`persistence`)에 먼저 기록한 뒤 지급한다.
- 모든 원장 이벤트에 유일한 `event_id`와 `source_system`을 부여. 외부 모드 이벤트 재호출에서도 같은 보상 두 번 지급 금지.
- 서버 메인 스레드의 월드 변경과 비동기 DB 저장 경계를 명확히 하고, 장애 시 재처리 큐 및 멱등성 보장.
- 백업: 월드·DB·설정·모드팩 버전·건팩·가구 풀을 **같은 복구 시점**으로 저장. 최소 1회 복구 리허설 필수.

### 14.3 가챠/거래 처리 의사코드(제안)

```text
ROLL_FURNITURE(player_uuid, pool_id, request_id, count):          # count = 1 | 10
  assert player.allowed and pool.active and now in [valid_from, valid_to]
  if request_id already processed: return saved result
  BEGIN TRANSACTION
    lock(wallet[player_uuid]); lock(gacha_state[player_uuid, pool_id])
    price = (count == 10) ? pool.price_10 : pool.price
    assert balance >= price
    debit(wallet, price, ledger_event=request_id)
    for i in 1..count:
      state.pity_counter += 1
      if state.wish_item != null and state.pity_counter >= pool.pity_k:
        item = state.wish_item; guaranteed = true                 # 선택 천장
      else:
        item = uniform_draw(server_rng, pool.items)               # 1/N, 등급 없음
      if owned(player, item): shards_gained = 1; state.shards += 1
      else: shards_gained = 0
      if item == state.wish_item: state.pity_counter = 0
      insert gacha_roll(request_id, i, pool_id, pool_version, item, guaranteed, shards_gained)
      grant_item_or_mailbox(item, grant_event=request_id + "#" + i)
    update gacha_state(version+1)
  COMMIT
  sync_client_result()

EXCHANGE_SHARDS(player_uuid, pool_id, item, request_id):          # 조각 교환
  BEGIN TRANSACTION
    lock(gacha_state[player_uuid, pool_id])
    assert state.shards >= pool.shard_cost and not owned(player, item) and item in pool.items
    state.shards -= pool.shard_cost
    grant_item_or_mailbox(item, grant_event=request_id)
  COMMIT

SET_WISH(player_uuid, pool_id, item, request_id):                 # 목표 변경 → 카운터 초기화
  state.wish_item = item; state.pity_counter = 0
```

`grant_item_or_mailbox`와 데이터베이스 트랜잭션이 물리적으로 동일 저장소가 아니라면 **outbox/지급 대기 상태**를 사용한다. DB 커밋 후 크래시가 발생해도 정확히 한 번 지급되도록 설계.

## 18. 운영 밸런스 측정과 조정 원칙

- **출시 전 측정:** 직업별 초급/중급/고급 구간에서 `Coin/hour`, 강화 1회 평균 비용, 일반 장비에서 보스 진입까지 걸리는 시간, 가구 1회 뽑기 비용의 체감 부담.
- **경제 목표(예시):** Coin 발행 총량과 Coin 소각 총량을 단기적으로 정확히 1:1로 고정하기보다, 신규 유저 초기 자본 축적·중견 유저 소비·고레벨 유저의 과잉 축적을 구분.
- **재화 수익 비교:** 직업을 바꾸지 않으면 도감과 보스가 막히는 구조 금지. 네 직업 중 최고 효율 하나가 시장 전체를 지배하지 않도록 NPC 매입량·시장 수요를 주기적으로 조절.
- **가구 뽑기:** 인게임의 장식 욕구를 Coin 소각으로 연결하되 강제 과금형 구조나 사행성 경쟁을 만들지 않는다. 기본 가구는 반드시 직접 구매 가능.
- **모드 업데이트:** 런처/클라이언트 자동 업데이트 계획은 이전 아이디어를 승계하되, **서버-클라이언트 버전 불일치 탐지 및 이전 버전 롤백**부터 구현.
- **[v0.2]** 경제·밸런스 점검은 G3 워크북(7.5장)의 Dashboard와 난수 시뮬레이션을 사용하고, 실측(P2 이후)으로 입력을 교체해 재계산한다.
